# One read-only memory MCP server, reached through hand-written tools

MCP (Model Context Protocol) is the standard way to offer tools to an LLM: a server lists its tools, and a client program calls them over the network when a model asks for one. The original brief had four MCP servers and connected them to the agent with LangChain's MCP package. The four were market data, the broker (the part that carries out the simulated buying and selling), memory, and Jev (the hosted decision model that picks and sizes the trades). Since ADR 0003 the LLM only selects episodes (the stored records of past decisions and how they turned out), and the memory search decision gave it exactly three tools, all of them read-only and all of them in memory: search episodes, read episodes in full, and read the track record (the agent's own scorecard of its closed trades, such as "18 trades, 5 wins, average loss of $12"). We decided that memory is the only MCP server and that it offers those three tools and nothing else. Market data, the broker, and Jev are plain Python modules inside the agent, and code writes to memory through a plain module too, including the LLM's one-line note from ADR 0003. The agent reaches the server with the official MCP SDK's own client (SDK version 2) and three tool definitions written by hand. We chose this because reliability comes first. Code calling code through MCP gains nothing and adds a network hop to every call, plus three more services that can fail and stop a run. Jev answers in about 0.17 seconds and is asked about each asset at every step where the asset has a bar, which is every 15 minutes while its market is open, so the hops add up. And a server with no write tools, logged in to Snowflake with a role that can only read, cannot place an order (an instruction to buy or sell, such as "buy $1,000 of this asset"), call Jev, or change memory, whatever the LLM asks of it.

## Considered Options

- **All four as MCP servers (the original brief).** More MCP to show, but slower runs and more moving parts, for tools no model calls.
- **No MCP server: the LLM's three tools as functions inside the agent.** The simplest option. Rejected: MCP is a requirement of the project, and the separate server is what lets the LLM's side of the system hold a read-only database role.
- **LangChain's current MCP package (`langchain[mcp]`, class `MCPAdapter`), which loads a server's tools automatically.** Rejected for now. Code fills in the run and the step on every tool call so that the LLM cannot ask about a later moment, and the LLM must not see those two inputs. As of 2026-11-13 the package has no documented way to hide an input from the model: its `@wrap_tool_call` hook lets code overwrite the two inputs, but the model is still shown them. The package is also marked beta ("The API may change").
- **The package the brief named (`langchain-mcp-adapters`).** Archived, and it only works with version 1 of the MCP SDK, which is in maintenance (critical and security fixes only).

## Consequences

- The brief's requirement of four custom MCP servers becomes one. Kubernetes runs three long-lived services (the memory server, the API, and the web app) plus the jobs.
- Each of the three tools is described twice: on the server, and in the agent's hand-written definition, which shows the LLM the tool without the run and the step and fills them in. A test compares the hand-written definitions with the server's own tool list, so a mismatch fails.
- A full evaluation is the path where the LLM selects episodes and Jev then picks a trade or no trade. Its first episode search, which code runs, goes through the same server tool the LLM uses, so both get the same search.
- The memory server gets its own Snowflake role, separate from the agent's, and that role can only read. It needs no permission for the embedding model: the memory search decision settled that text is embedded only when a dataset is built, never during a run.
- The LLM's tool loop is a small LangGraph graph of our own (model call, tool calls, repeat). The limits are 6 tool calls and 60 seconds per full evaluation, then one last model call with the tools removed; LangChain's ready-made limits cannot remove the tools for a last call and have no time limit.
